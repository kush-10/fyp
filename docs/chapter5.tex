\chapter{LowMC vs AES Analysis}

\section{Why LowMC Should Be Faster (Theory)}

LowMC is widely discussed as a ZK-friendly design because it targets low
multiplicative complexity and minimizes nonlinear gates. Under circuit-centric
reasoning, fewer nonlinear components often imply lower proving cost.

This creates a clear theoretical expectation for circuit-oriented
verifiable-computation settings: LowMC should be competitive, and potentially
faster, when nonlinear gate pressure dominates cost
\cite{albrecht2015ciphers,jaques2019grover}.

That expectation is reasonable at the design level, but it does not by itself
predict end-to-end zkVM runtime. This chapter therefore compares theory against
receipt-backed measurements from the implementation used in this project.

\section{Surprising Result: LowMC Is Not Fast in This zkVM}

Measured results in this project do not match the circuit-level expectation. In
the current RISC Zero implementation, LowMC is slower than AES on core proving
metrics.

\section{Comparison with Related Work}

Prior work motivates LowMC by low multiplicative complexity and strong
performance potential in circuit- and MPC-oriented settings
\cite{albrecht2015ciphers,jaques2019grover}. The measurements in this chapter
do not contradict that design motivation; instead, they show a deployment-level
boundary: those gains do not automatically transfer to VM-trace cost in this
implementation stack.

Similarly, ZK-friendly primitive literature often reports constraint-level
benefits for circuit-native constructions. This dissertation's contribution is to
show that VM-level software costs can dominate and reverse expected rankings.

The comparison is therefore best read as a transferability result. LowMC remains
well motivated when the implementation target is a circuit whose cost is closely
related to nonlinear gates. In this dissertation, however, the implementation
target is compiled Rust guest code inside RISC Zero. The cost surface includes
instruction count, memory movement, guest serialization, and trace expansion.
Those costs are visible to the prover even when they are not captured by the
primitive's circuit-level design goal.

\section{Root Cause Analysis}

The likely causes are implementation and VM effects rather than algorithm intent
alone:

\paragraph{Software overhead.}
Abstract gate counts do not include many software costs that appear in a real
zkVM run, such as memory movement, serialization boundaries, and repeated state
transformations in guest code.

\paragraph{Matrix-path pressure.}
LowMC's linear layers require matrix-heavy operations. In this implementation,
those paths create substantial trace and runtime pressure. The important detail
is how that pressure is represented in RISC Zero: LowMC is not turned directly
into a hand-authored arithmetic circuit. Instead, the Rust guest implementation
is compiled to RISC-V code, the VM records the executed instruction stream, and
the prover arithmetizes that execution trace as polynomial constraints.

For LowMC specifically, the matrix path begins as binary matrix data plus Rust
loops that apply each row of the matrix to the current cipher state. The state is
held as packed machine words, so each output bit is computed by selecting state
words, masking or shifting the relevant bits, XOR-accumulating parity, and then
writing the resulting packed word back into the next state. After compilation,
that high-level matrix--vector product is no longer a single algebraic object: it
is a sequence of RISC-V loads, stores, branches, shifts, ANDs, ORs, and XORs.
RISC Zero then proves the correctness of those executed instructions. Each loop
iteration contributes register transitions, memory accesses, and control-flow
steps to the VM trace, and the arithmetization constrains that trace rather than
the original LowMC matrix equation directly.

This distinction matters because the LowMC matrix is applied over the full
256-bit state and repeated once per round. In a circuit-native implementation,
the designer can express the linear layer as a compact network of XOR constraints
and reason mainly about nonlinear-gate count. In the zkVM implementation used
here, the path is created operationally every time the compiled guest executes
the matrix loop. The cost therefore grows with state width, matrix density, round
count, and the overhead of representing the matrix and state in memory. This is
why a construction that looks cheap under nonlinear-gate counting can still
create a long VM trace.

\paragraph{Trace expansion effects.}
Repeated bit-level transforms and state updates inflate execution traces, which
raises proving work even when the design target is ``ZK-friendly'' at circuit
level \cite{risczeroTraceDocs}.

\paragraph{VM-vs-circuit optimization gap.}
This project optimizes Rust guest code running on a zkVM; it does not optimize a
custom arithmetic circuit. Circuit-intuition advantages therefore do not automatically
transfer to VM-level proving advantages.

Supporting pprof evidence makes this explanation more concrete. The entries in
Table~\ref{tab:lowmc-pprof-top-views} were extracted with \texttt{go tool pprof

This supports the root-cause explanation in two ways. First, optimisation of
LowMC internals gives a real improvement, so the implementation path is part of
the cost. Second, the improvement is not enough to approach AES, so the gap is
not explained by one removable inefficiency alone. The remaining difference is
consistent with repeated matrix and bit-level work accumulating across the full
guest trace.

\section{Optimisation Approaches and Evidence Trail}

\subsection*{Changes Applied to LowMC}

Optimisation work on the LowMC guest targeted the following concrete areas:

\paragraph{SWAR-style substitution layer restructuring.}
The original S-box layer applied nonlinear substitution word-by-word using a
loop over individual state elements. The optimised path restructures this into a
SWAR (SIMD Within A Register) pattern: multiple state words are packed together
and processed with combined bitwise AND, XOR, and rotation operations that
exploit register-level parallelism within the 32-bit RISC-V instruction set.
This reduces loop iterations and associated branch and load/store overhead in the
guest trace.

\paragraph{Matrix hot-path cleanup.}
LowMC's linear layer requires multiplying a large random binary matrix against
the full cipher state. The baseline implementation accumulated unnecessary
temporaries during the matrix apply step. The optimised path reduces allocation
pressure and simplifies the inner loop structure, which reduces memory movement
visible in the guest execution trace.

\paragraph{Precompute-oriented host/guest input contract.}
The baseline LowMC guest generated random round-key and matrix material from a
seed at the start of each execution. In a zkVM, this setup work runs inside the
guest and contributes fully to the proven trace. The optimised path moves this
precomputation to the host: the host generates and serializes the matrices and
round keys before invoking the prover, and the guest receives them as direct
inputs. This removes the setup cost from the proved trace entirely, at the cost
of larger input serialization. As the pprof profiles show, this exposed a new
bottleneck: guest input deserialization via \texttt{sys\_read\_words} and
\texttt{FdReader::read\_words} became the dominant cost after setup was removed.

\paragraph{Round-count control.}
A configurable round-count parameter was added to allow controlled experiments
with reduced round counts. This does not affect the final reported benchmark
values (which use the full LowMC round count for a fair comparison), but it
provided a useful tool for isolating whether matrix multiplication or the
round-function overhead was the dominant cost at different circuit depths.

\subsection*{Changes Applied to AES}

An AES optimisation workspace was also implemented, targeting the S-box backend.
The specific change explored was swapping from a lookup-table representation
(where SubBytes is implemented as a 256-entry byte table indexed by the input
byte) to a bitsliced logic representation (where the S-box is computed as a
sequence of bitwise AND, XOR, and NOT operations over packed state). In a zkVM,
these two representations have different trace shapes: table lookup requires a
random-access memory read (load from a table), while the logic circuit requires
more arithmetic instructions but no data-dependent memory access. Under RISC
Zero's execution model, the logic circuit path was expected to reduce cache
pressure and randomize the trace less, potentially improving proving regularity.

Benchmark results show that the latest available standalone AES backend snapshot
does produce a measured reduction (Table~\ref{tab:aes-backend-snapshot}), but the
snapshot is single-trial and outside the final CTR/CTR+HMAC report matrix. It is
therefore useful optimisation evidence, not a replacement for the repeated
authenticated-pipeline comparison.

\section{Takeaway}

The practical conclusion is that LowMC should not be selected for the final
authenticated pipeline in this repository. It is still valuable as a negative
result because it demonstrates exactly why the project benchmarked primitives
inside the target zkVM instead of importing a circuit-level ranking. AES becomes
the better engineering choice not because it is theoretically more ZK-friendly,
but because it is measurably more suitable for this implemented VM workload.
